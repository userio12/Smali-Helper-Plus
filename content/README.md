# Documentation content and update manifest

The app ships its documentation (opcodes, lessons, built-in snippets) as JSON in
`app/src/main/assets/content/`. Optionally, users can download newer versions of the same JSON files. This directory is
what the app downloads from:

```
https://raw.githubusercontent.com/riyadmondol2006/Smali-Helper-Plus/main/content/manifest.json
```

(The address is `BuildConfig.DEFAULT_CONTENT_MANIFEST_URL`; users can override it under *Documentation updates >
Advanced*.)

## Files

| File | Purpose |
| --- | --- |
| `manifest.json` | Index of the available packages with checksums |
| `opcodes.json`, `lessons.json`, `snippets.json` | Byte-for-byte copies of the bundled assets, generated by the script |

**Do not edit these files by hand.** Edit the files in `app/src/main/assets/content/`, bump `contentVersion` in the
changed file, then run:

```sh
python3 scripts/build-content-manifest.py                      # copy files + write manifest.json
python3 scripts/build-content-manifest.py --check              # CI: fail if content/ is out of date
python3 scripts/build-content-manifest.py --description lessons="Two new lessons about try/catch"
```

The script uses only the Python standard library, validates the bundle headers, computes the real SHA-256 and size, and
is idempotent (`publishedAt` only changes when a package changes). The `manifest.json` committed before the bundled
content existed contains placeholder checksums (all zeros, size 1); it is harmless because every package there is
version 1 (equal to the bundled version, so it is ignored) and a checksum mismatch is rejected. Run the script once the
bundled files are final to replace it.

## Manifest format (`schemaVersion` 1)

```json
{
  "schemaVersion": 1,
  "publishedAt": "2026-10-31T00:00:00Z",
  "minAppVersionCode": 1,
  "packages": [
    {
      "id": "opcodes",
      "contentVersion": 2,
      "url": "https://raw.githubusercontent.com/riyadmondol2006/Smali-Helper-Plus/main/content/opcodes.json",
      "sha256": "<64 lower-case hex characters>",
      "sizeBytes": 123456,
      "description": "What changed, shown to the user before installing"
    }
  ]
}
```

| Field | Rules |
| --- | --- |
| `schemaVersion` | Must be `1`. Any other value is rejected ("format version not understood"). |
| `publishedAt` | Informational ISO-8601 timestamp. |
| `minAppVersionCode` | Lowest app `versionCode` able to read the packages. If the installed app is older, nothing is offered and the user is told to update the app. |
| `packages[].id` | `opcodes`, `lessons` or `snippets`. Each id at most once. |
| `packages[].contentVersion` | Integer >= 1. A package is offered only if it is **strictly higher** than the installed `contentVersion`; older or equal versions are ignored. It must equal the `contentVersion` inside the package file. |
| `packages[].url` | Absolute **HTTPS** URL, no credentials. Redirects that change the scheme are not followed. |
| `packages[].sha256` | Lower-case hex SHA-256 of the exact bytes served at `url`. |
| `packages[].sizeBytes` | Exact size in bytes, 1 to 5 242 880 (5 MB). The download is aborted as soon as it exceeds this value; a smaller body is rejected too. |
| `packages[].description` | Short release note. |

The manifest itself must be smaller than 256 KB.

### Package files

A package file is exactly one of the bundle DTOs from `core/content/ContentModels.kt` (`OpcodeBundleDto`,
`LessonBundleDto`, `SnippetBundleDto`), with `schemaVersion` 1 and the `contentVersion` announced in the manifest. After the
checksum matches, the app decodes it into those typed DTOs and runs `ContentValidator` (duplicate ids, unknown categories,
invalid formats, non-HTTPS references, quiz indices ...). Anything that fails is discarded.

## Client behaviour (for reference)

1. *Check*: download the manifest, validate it, compare with installed versions. A failed request is shown as an error,
   never as "up to date". The result of the last successful check is remembered so the Updates screen can show a badge.
2. *Install*: all selected packages are first downloaded and fully verified (size, SHA-256, JSON, validator) without touching
   the database. Only then are they written, **one atomic Room transaction per package**. If package 2 of 3 fails to
   write, package 1 stays installed and valid, package 2 is rolled back and keeps its previous content, and the user is told
   exactly what happened. User data (bookmarks, user snippets, progress, history) is never touched.
3. *Restore bundled content*: reinstalls the three JSON files from the APK even when a downloaded version is newer.
4. Downloaded files are data only. Nothing is ever executed, and only HTTPS is used.
5. Background checks (optional, weekly, connected network, battery not low) only check; they never install anything.

## Publishing a new content version

1. Change the JSON in `app/src/main/assets/content/` and increase its `contentVersion`.
2. `python3 scripts/build-content-manifest.py --description <id>="what changed"`
3. Commit `content/` together with the assets and push to `main`. `raw.githubusercontent.com` serves the new files within a few
   minutes (it is cached); apps ignore a manifest whose checksums do not match the files they download, so a half-published
   state cannot install corrupt content.
